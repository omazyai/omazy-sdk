# Changelog

The TypeScript, Python and Go clients share one version number.

## 0.5.1 (2026-11-24)

The fixes from the sixth independent review of the `oauth` kit, and the end of its review warning.

Six independent reviews of the `oauth` kit are done. The last one found nothing high and no unconditional medium, and its findings are fixed below. Each review's proofs run as regression tests. The kit stays a preview, like every kit: pin the exact version.

A door may now open with it, as long as the product follows the setup rules on the kit's reference page: `platformDoors` named, a list of known clients on every platform door, `checkSeat`, a consistent refresh store (the Durable Object or D1), the rate-limit bindings, and `@cloudflare/workers-oauth-provider` pinned at the tested version.

Upgrading from 0.5.0: `RefreshStore` has five new methods, so a custom store must implement them. On D1, run `applyOAuthD1Migrations` again (migration `0003_oauth_person_index`, additive). `checkSeat` is now required at every door. Everything else is unchanged in name and shape.

Fixes from the sixth review of the `oauth` kit:

- `personLostRole`, `revokeApp` and `connectedApps` no longer find a person's grants and keys by KV's `list()` alone. KV's listing is eventually consistent, so a grant or key made in the last minute or so was missing from it: `personLostRole` returned `{ grants: 0, keys: 0 }` for a grant and a key made ten seconds earlier, and both kept working (the grant refreshing for good). The refresh store now keeps an index per person, written when a grant is made (before the client has its code, failing closed) and renewed on every refresh, and when a key is minted; the three functions read it, with KV's listing for older records. `personLostRole` first records a revocation of the person (at the door or tenant given) in the store, for a little over a year: anything made for the person before that moment is refused at its next refresh, code exchange or `resolveSeat`, even if the index missed it, and a grant is revoked there (new event `grant_revoked`, reason `person_revoked`). `RefreshStore` has five new methods (`indexPut`, `indexDelete`, `indexList`, `revokePerson`, `personRevocations`), which a custom store must implement. D1 needs the new tables: run `applyOAuthD1Migrations` again (migration `0003_oauth_person_index`, additive); `prune` clears them. The Durable Object keeps them in objects of the same class, with no new migration.
- `checkSeat` is required at every door, a tenant door too; without it `authorizationServer` throws at start. It also runs inside the library (its `tokenExchangeCallback`) on every refresh and code exchange, before any token is minted: a seat it says is gone revokes the grant, tombstone first (`grant_revoked`, reason `seat_gone`), and a throw answers `503` and revokes nothing, leaving the refresh token good for the retry. Before, a tenant door could omit it, with a start-up warning that said a removed seat kept working until its access token expired; in fact its grants kept refreshing, and with `checkSeat` its access tokens stopped but the grant kept refreshing. The warning is gone with the option's optionality.
- Key revocation no longer lives only in KV. With a refresh store, a revoked key gets a tombstone there before its KV records are deleted, and `resolve`, `list` and `transferService` read it, so a revoked key stops at once in every location. `transferService` refuses a revoked key (false): a location whose KV cache still held it wrote it back for good, under its new owner. A key moved with `transferService` is covered by its new owner's revocations from the moment it moved. `Keys` takes the store as an optional fifth argument, and `authorizationServer` passes its refresh store to its keys. `@omazyai/sdk/oauth/keys` exports `durableObjectRefreshStore`, `d1RefreshStore`, `applyOAuthD1Migrations`, `OAuthRefreshLock` and `kvRefreshStore`, and still loads no provider. Without a store, `Keys` works as before, with the KV window, now documented. Joya, on keys with KV alone, should bind the `OAuthRefreshLock` Durable Object (or its D1) and pass that store to `authorizationServer` and to any `Keys` it builds in the Worker.
- Every numeric option is a whole number, checked at start: `keys.personal.maxDays`, `keys.service.maxDays`, `registration.perHourPerIp`, `perHourPer48` and `clientTtlDays`, `turnstile.after`, `ttl.accessSeconds` and `ttl.refreshSeconds` (at least 60), and `signInCodes` `ttlSeconds`. `NaN`, `Infinity`, a fraction or zero throws. Before, `NaN` passed every comparison and lifted the limit: `maxDays: NaN` minted a ten-year personal key, `perHourPerIp: NaN` removed the registration limit, `turnstile.after: NaN` never showed the challenge.
- `oauth.api()` returns the library's helpers with `revokeGrant` and `deleteClient` going through the kit: `revokeGrant` tombstones the grant first, as `revokeApp` does, and `deleteClient` tombstones and revokes every grant of the client (found through a new per-client index in the refresh store and a listing of every grant in KV) before the library deletes the client. Before, a grant revoked through `api()` came back from a location whose KV cache still held it.
- A tenant door on the KV refresh store warns at start, unless `refresh.acceptKvRace` is set: there a replayed refresh token, a revoked grant or key, and a person who lost a role keep working for about 60 seconds in another location.
- `signInCodes(kv, { store })` takes the refresh store. With a consistent one, a redeem claims the code there under a lock, so a code is single use across locations; before, a location whose KV cache still held a redeemed code could redeem it once more with the same flow's state. Without a store nothing changes.
- The docs say that revoking an access token alone (RFC 7009) is the library's KV delete, with no tombstone, so other locations stop accepting it within about 60 seconds; revoking the refresh token or calling `revokeApp` stops the grant at once.

## 0.5.0 (2026-11-24)

The product kits and `create-omazy-app`, as a preview.

**Everything new in this release is a preview.** The kits and the scaffolder may change their names and their shapes before 1.0. Pin the exact version, read this changelog before moving to the next one, and expect to change code when you do.

**The `oauth` kit is still under independent security review. Do not open a door with it in production yet.** Five reviews found issues, and each one is fixed with a regression test (listed below), but the review is not finished.

What is in it:

- The kits, TypeScript only, each its own entry point: `@omazyai/sdk/capabilities` (one definition of each action), `/guard` (who may run it, confirms, approvals, switches, limits, a request log), `/mcp` (an MCP server per door), `/oauth` (the authorization server for those doors), `/ai` (the run layer every model call passes through), `/ai-sdk` (a Vercel AI SDK model on that run), `/actors` (a form as a conversation), `/flows` (workflows and automations, each step in a ledger), `/copilot` (an open conversation on the product's data, streamed to `useChat`), `/ui`, `/ui/react` and `/ui/server` (the screens and their routes) and `/testing` (unit, actor and door tests without the network, and release gates).
- `create-omazy-app`, a new package versioned with the SDK, which writes a new product on the kits. Its `package.json` pins the SDK release tarball of the same version.
- Model roles, tags and cost, and spend caps on the Core API, in all three clients.
- Fixes to the 0.4.x clients: the response details of one call (`withResponse`, `with_response`, `WithResponseInfo`), so a Worker serving requests at once reads its own; a 30 second timeout on live transcription `commit()` and `end()` in TypeScript; and retries after a 429, a gateway error or a dropped connection for document changes, document deletes and MCP server removal.
- `@omazyai/sdk` and `@omazyai/sdk/server` are unchanged in name and shape: code written for 0.4.0 runs unchanged. The TypeScript package now says Node 20 or later, which is what it already needed.

The details, kit by kit:

The `capabilities` kit, experimental: the first of the product kits. TypeScript first; the Python and Go clients stay API clients. Nothing in 0.4.0 changed its name or its shape, and `@omazyai/sdk/server` is unchanged.

- A new entry point, `@omazyai/sdk/capabilities`. Each action a product offers is defined once with `capability({ ... })`: a `<noun>_<verb>` name, the doors (audiences) that see it, a title, a description of 80 to 600 characters written as a prompt, synonyms, an opaque permission for the product's own check, a risk tier R0 to R4, an approval policy name (required at R3 and R4), input and output schemas, the fields that hold personal data, a version, and `preview` (required at R2 and above) and `run`. A definition that breaks a rule throws when the module loads, listing every problem.
- `defineCapabilities<Ctx, Permission, Door>()` binds the product's own context, permission and door types once. `Ctx` carries the principal, seat, tenant, channel, approval id and request id, plus the product's own fields.
- Schemas: any Standard Schema that also gives Standard JSON Schema, so zod 4.2 and later works as is. Valibot, TypeBox and others go through `withJsonSchema`. The `schema` helpers (object, text, id, integer, minorUnits, enum, array and more) do the same with no dependency. Every object in the JSON Schema is closed with `additionalProperties: false`. `parse` refuses a field the closed JSON Schema does not name, at any depth, even when the library would drop it (zod's plain `z.object`).
- `registry([...])` lists capabilities by door and gives the MCP tool list (`inputSchema`, `outputSchema` and annotations), the tool definitions for `ai.complete`, a form schema, argument parsing with the tier of the call, redaction of personal fields for logs (capped at 4 KB without splitting a character) and BM25 tool search over names, descriptions and synonyms.
- Read or write, and the MCP hints, come from the tier and are never stored. Anything that is not R0 to R4 counts as R4. R3 and R4 are marked destructive.
- `riskFor(input)` lowers the tier for some inputs (turning a kill switch off). It never weakens caution: a tier above the declared one is used and reported, and anything that is not a tier counts as R4.
- Versioning: `snapshot()` gives the catalog as data to commit. `assertAdditive(before, after)` fails on any change that would break a client: a removed field, a new required field, narrower values, an output field that may now be missing, a schema change without a new version, or a capability removed before its deprecation date (90 days by default). `toolsChangelog(before, after)` writes the tools changelog.
- `reg.parity({ ... })` and `assertParity` for a product's CI: every entry is sound, names are unique, and no surface names a tool the registry lacks or one its door cannot see.
- `parityProblems` and `assertParity` take `surfaces` as the same record `reg.parity` takes (`Surfaces`: a name to a list of tools, or to `{ audience, tools }`). The array form `[{ name, audience?, tools }]` still works and is deprecated; it goes before the first release.

The `guard` kit, experimental: whether a capability call runs, who decides the sensitive ones, and a record of every request.

- A new entry point, `@omazyai/sdk/guard`. `createGuard({ registry, can, secret, store, policies, ... })` takes the product's pieces: its permission check, policy table, record-owner lookup, roles, step-up verifiers, switches, rate limiter and request log.
- `guard.call(ctx, name, args, { confirmToken?, waitUntil? })` checks, in order, kill switches, rate limits, the arguments, the tenant and the product's `can()`, and the tier, then runs R0 and R1 (R1 masked), asks for a confirm at R2 and holds R3 and R4 for a person. It never throws: the outcome is one of `ok`, `confirm_required`, `pending_approval`, `refused_permission`, `refused_tier`, `read_only`, `stale`, `rate_limited`, `invalid`, `switched_off` or `error`, with a plain sentence.
- Confirm tokens: an HMAC over the seat, the tool, the hash of the canonical arguments, the preview's state version and a nonce kept 10 minutes. Single use, bound to the arguments, `stale` when the target moved.
- Approvals: the arguments sealed with AES-GCM and hashed, the preview, the policy and the expiry. The approver comes from the policy table: `approver.authorOrRecordOwner()`, `approver.role()`, `policies.single()` and `policies.fourEyes()`. Every decision needs a step-up proof; a refusal needs a reason; decisions are a compare-and-swap. Execution re-checks both people as of now, re-runs the preview, refuses `stale` when the state moved and runs the stored arguments once, idempotent on the approval id. A tenant's own policy can only tighten the base.
- `guard.withdraw(id, ctx, reason)` takes back a waiting approval: a compare-and-swap from `waiting` to the new status `withdrawn`, so it is never decided or run. Only its requester (same principal, same tenant) or a principal of kind `system` (`SYSTEM_PRINCIPAL_KIND`) may, with a reason kept on the row. Every attempt is logged as `approval/withdraw`, and `onApproval` gets a `withdrawn` event. A flow waiting on a withdrawn approval ends `refused` with `approval_withdrawn`.
- `codeStepUp()` sends and checks one-time codes (one channel, or two for a super admin without a passkey); a passkey is the product's own verifier.
- Kill switches by key (`all`, a door, a kind of caller, a tool, the product's own) at global, tenant and person scope, read deny first on every call with no cache.
- `guard.doorSwitch(door, ctx?)` reads only the `all` and `door:<door>` switches, for a door that must stop every request and not only tool calls. It returns the first one that is off, or null, and throws when the switches cannot be read.
- Rate limits through Cloudflare Rate Limiting bindings, per seat for reads and writes and per tenant.
- A request log row per call, arguments redacted through the capability's personal fields, written after the response so it never delays or fails a call; listings sampled one in ten; `logAnonymous()` records a request refused before it had a principal as `refused_auth`. The request id travels in `X-Omazy-Request-Id`.
- `auditStatement()` for the product's own audit row with `via`, `approval_id` and `request_id`, in the same batch as the change. `purgeTenant()` deletes a tenant's rows in resumable chunks within D1's limits, with tables and rows to keep.
- Stores for Cloudflare D1 (`d1GuardStore`, `d1RequestLog`, `d1Switches`, with the SQL in `GUARD_MIGRATIONS`) and in memory for tests. Web standard APIs only.

The `mcp` kit, experimental: an MCP server per door, built from the registry and the guard.

- A new entry point, `@omazyai/sdk/mcp`, on the official MCP TypeScript SDK v2. Install `@modelcontextprotocol/server` 2.4.0 beside the SDK; it is an optional peer dependency, so a product that does not serve MCP installs nothing more.
- `mcpServer({ registry, guard, door, resolveSeat, info })` returns a Worker-shaped `fetch` for one door. It serves spec revision 2026-07-28 (no sessions, no `initialize`, `server/discover`, `input_required`) and, statelessly, 2025-11-25, 2025-06-18 and 2025-03-26 clients, each request by a fresh server and answered as one JSON body. JSON-RPC batches are accepted only on 2025-03-26. Schemas are checked with the SDK's `cf-worker` validator, so nothing compiles code at runtime.
- Tools come from the registry for the door, in registry order, with annotations from the tier, `outputSchema` and `structuredContent`, and cursor paging (50 a page by default). `tools/list` carries a one-minute private cache hint for 2026-07-28 clients. A seat may carry `maxTier` (a personal key) or an allow list of tools (a service key); tools above it are neither listed nor callable.
- Every `tools/call` goes through `guard.call`. `confirm_required` becomes an `input_required` elicitation on a 2026-07-28 client that can answer one, and a result with the preview and the confirm token otherwise; the client sends the token back as the `confirm_token` argument, which the kit adds to every tool at R2 and above. `pending_approval` becomes a result with the decider, the expiry and the review link. Refusals are `isError` results with the guard's sentence, validation issues listed. A failure inside is a generic sentence with a reference, and the `onError` hook gets the error. A switch that turns the whole door off answers 503.
- Doors: `resolveSeat(token, req)` turns the bearer into a seat; a seat for another door is refused with 401 `invalid_token`. `mcpDoors(a, b, ...)` serves several doors from one Worker, each at its own path. OAuth comes with the `oauth` kit.
- Resources and prompts from plain lists, `notifyToolsChanged()` for `notifications/tools/list_changed` to 2026-07-28 clients, and the guard's request log for every request that is not a tool call. An auth refusal (`no_token`, `bad_token`, `wrong_door`) is logged through `logAnonymous`, never sampled. Every answer carries `X-Omazy-Request-Id`.
- The door switch (`all` or `door:<door>`) stops every request, not only tool calls: `initialize`, `tools/list` and the rest answer 503 with one plain sentence (the switch's reason, `doorOffMessage`, or "This door is switched off right now.") and a request-log row with the outcome `switched_off` and the code `door_off`. A global switch is read before the token; a tenant or person switch once the seat is known. Switches that cannot be read count as off. Joya checked the switch itself in front of the door; it no longer needs to.
- A call to an unknown tool, or one above the seat or outside its allow list, is still a protocol error, and is now a request-log row through the guard: method `tools/call`, the tool name, the outcome `invalid` (as the guard gives an unknown tool; no new outcome) and the code `unknown_tool`, `tier_above_seat` or `not_in_allow_list`.
- `@omazyai/sdk/server` and its `serveMcp` are unchanged and stay dependency free. The kit is what to move to; the reference page has the steps.

What a second product found moving onto the `capabilities`, `guard` and `mcp` kits, fixed in the kits so it needs no shim of its own:

- `say(output, ctx)` on a capability sets the text a model reads for a completed call. `structuredContent` stays the JSON; without `say` the text is the JSON, as before.
- `confirm: 'upstream'` on a `SeatGrant`, and `{ confirm: 'upstream' }` on `guard.call`, for a caller that confirms with the person itself (Omazy's agent with `write_mode: 'confirm'`). Its R2 calls run in one call: the guard still mints and checks the token, refuses a stale preview and logs both steps. Its tools carry no `confirm_token` argument. R3 and above are unchanged. This is the fix for the double confirm.
- The `mcp` kit answers 2024-11-05 clients, served statelessly like 2025-03-26, batches included. `accept2024: false` turns it off.
- The kit's 2025 and 2024 leg serves a request without an `Accept` header and a JSON body sent as `text/plain`, form data or with no content type. An `initialize` without `protocolVersion`, `capabilities` or `clientInfo` gets `-32602` with one plain sentence instead of the MCP SDK's validation dump. 2026-07-28 is left as strict as the spec.
- `unknownFields: 'refuse' | 'strip'` on a capability. `refuse` stays the default; `strip` drops an argument the schema does not name, runs the call and writes the dropped paths to the request log as `stripped:<paths>`. `invalidMessage(issues)` gives the one sentence for an `invalid` call, and the MCP result then carries only that sentence.
- A guard call reads every switch key it needs in one read, once, an upstream-confirmed write included. `d1Switches(db, { cacheMs })` can keep a read for that long; the default is 0, and a cache delays an emergency stop by up to that long.
- `createGuard({ ..., ephemeral: true })` for a stateless door: no store, no secret, confirm nonces in memory for one call. It runs R2 only when confirmed upstream and refuses R3 and above (`refused_tier`, `no_approvals`), so it cannot hold a confirm or an approval it would lose.
- `guard.http(req, { principal, seat, channel: 'rest', ... })` gives a REST route its ctx, `call` through the guard and request log (method `POST /path`), an HTTP status for each outcome and the request id header.
- A `not_found` outcome, distinct from `invalid`, for a lookup that finds nothing.
- `capabilities.tools.listChanged` is true only for 2026-07-28 clients, which can receive the notice; 2025 clients served statelessly get false.
- The capabilities page says how to tier a write that reaches only the product's own staff.

Models on the Core API (RFC 2288 AL-10), in all three clients. Each needs a deploy of the API to answer:

- `response_format` on `ai.complete` and `ai.stream`: `{ type: 'json_object' }`, or `{ type: 'json_schema', json_schema: { name, schema, strict } }`. The result's `text` is the JSON and the new `output` is the same value, checked against the schema. With `strict`, every object in the schema must be closed and every property required.
- `tool_choice` takes `{ type: 'tool', name }` to make the model call that tool. Go: `omazy.ForceTool(name)`, with `omazy.ToolChoiceAuto`, `ToolChoiceAny` and `ToolChoiceNone`; `ToolChoice` is now a `*ToolChoice`, not a string.
- `images` on a user message: `{ url }` (https) or `{ data, media_type }` (base64).
- A call that asks the chosen model for something it cannot do is a 422 `MODEL_UNSUPPORTED`.
- `ai.embed(input)` (`AI.Embed` in Go): vectors for one text or up to 128 with the deployment's embedding model. `ai.models()` (`AI.Models`): the models the install may name and what each can do. Both under `ai:complete`, and both retried like a read.

The `oauth` kit, experimental: the MCP authorization server a product mounts beside its doors. Workers only.

- A new entry point, `@omazyai/sdk/oauth`, on `@cloudflare/workers-oauth-provider`, pinned at 1.3.0 as an exact optional peer dependency. The library does the protocol (RFC 8414 metadata, the token endpoint, exact redirect URIs, resource-bound grants, hashed storage, Client ID Metadata Documents, optional RFC 7591 registration). Storage is a KV namespace; `memoryKv()` stands in for tests.
- `authorizationServer({ issuer, kv, doors, signIn, chooseSeat, ... })`. `route(req)` serves RFC 9728 metadata per door, `/authorize`, `/oauth/callback`, `/oauth/token` and, when switched on, `/oauth/register` (rate limited per address). `door(name)` gives `mcpServer` its `resolveSeat` and the metadata URL for the 401 challenge.
- Every authorization request must name one door as `resource` and use PKCE S256, confidential clients included.
- The consent page: single-use handle bound to the browser, `frame-ancestors 'none'`, no cache, every client string escaped, the client's name and whether it is known, verified by its metadata document or not verified, the redirect host, a loopback warning, Turnstile after repeated attempts. A client policy per door: a `known` list by client id or metadata domain, and `others` and `unverified` set to allow or block. Unverified clients are blocked unless a door allows them.
- Sign-in through the product: the consent page sends the browser to the product's sign-in, which returns a one-time code; `authenticate` redeems it over the back channel and `chooseSeat` picks the seat. `signInCodes(kv)` is a ready-made code store.
- Tokens: access 1 hour, refresh 30 days, rotated on every use and bound to client and door. A rotated refresh token presented again revokes the whole grant. A token holds only the person and the seat; `checkSeat` and the guard's `can()` decide on every call.
- `connectedApps(person)`, `revokeApp`, `personLostRole(person, { door, tenant })`.
- Keys: `keys.createPersonal` (a prefix per door, at most 90 days, at most R2) and `keys.createService` (one tenant, a tool allow list, at most 365 days). Shown once, stored hashed, listed, revoked, and moved to another owner with `keys.transferService`.
- `Keys` has its own entry, `@omazyai/sdk/oauth/keys`, with its constants, its types and `memoryKv`. It loads neither `@cloudflare/workers-oauth-provider` nor `cloudflare:workers`, so a Node script or a plain bun test mints a key with no stand-in and no warning from the provider. `@omazyai/sdk/oauth` still exports `Keys`; nothing else changed.
- The reference page has a threat model and a checklist for a second security review, which is due before any door opens with the kit.

Fixes from the second security review of the `oauth` kit:

- The token endpoint reads the body exactly as the library does (the media type split on `;`, trimmed and lower-cased; no parameter but `resource` repeated) and refuses any POST it cannot read. Before, a rotated refresh token sent with `Content-Type: Application/x-www-form-urlencoded` skipped the reuse check and locked the real client out.
- A sign-in code is bound to the flow it was issued for. `signInCodes(kv).issue(person, { state })` stores a hash of the upstream state, `redeem(code, state)` refuses another flow's state, and `signIn.authenticate` is now `(code, state, req)`, with the state the callback carried. Before, a victim's leaked code finished an attacker's own flow, and the attacker's client got the victim's seat. `oauth.callbackUrl` is the exact URL a sign-in page compares `return_to` to.
- `known` takes exact client ids only (the full metadata document URL, or a pre-registered id); a bare domain there throws at start. Matching by metadata host moves to an opt-in `knownDomains`, which also requires every redirect URI in the document to stay on that host and is refused on a platform door. A document whose redirect URIs leave its own host counts as unverified. A metadata URL that answers with a redirect is refused: the library follows redirects and has no fetch hook, so the kit checks the URL itself with `redirect: 'manual'`. New option `platformDoors` (default: the door named `platform`) and event `client_metadata_refused`.
- Error redirects from `/authorize` go only to a client the door knows. The client's status is worked out first; a blocked, unverified or verified client, and a request without a valid `resource`, get a page on the kit's own origin (403 for a blocked client, 400 otherwise). Before, any blocked or registered client could use the authorization origin as an open redirect to its own URI.
- A refresh takes a lock per grant, so two refreshes of one grant at once cannot both pass; the second gets `invalid_grant` and `onEvent` gets `refresh_contended`. `refresh: { store }` picks where the lock and the rotated-token marks live: `durableObjectRefreshStore` (with the `OAuthRefreshLock` Durable Object class the product binds) or `d1RefreshStore` (tables in `OAUTH_D1_MIGRATIONS`, `applyOAuthD1Migrations`). The default stays on KV with a lock per isolate, which leaves a replay from another region open for about 60 seconds; a platform door refuses it unless the product passes `acceptKvRace: true`.
- A withdrawn metadata document stops working at once: the kit passes `clientIdMetadataDocumentFallback: false` to the library, whose last-good copy otherwise answered for 24 hours after a 404. `clientMetadataFallback: { maxAgeSeconds }` (60 to 3600) turns a short copy back on.
- Service keys: capped at R2 unless `keys.service.maxTier` says otherwise (`SERVICE_DEFAULT_TIER`), and refused at a platform door unless `keys.service.platformDoors` lists it. A tier in the key options that is not R0 to R4 throws at start; before, a misspelt tier ranked above R4 and capped nothing.
- `checkSeat` is required when there is a platform door, and the kit warns at start when it is missing elsewhere. `rateLimit.authorize` takes a Workers Rate Limiting binding and counts every GET `/authorize` per address before any KV write (event `authorize_limited`, a 429 page); the kit warns at start without it. A person id that starts with a key prefix is refused at sign-in, and a token with `:` is never read as a key. The last-use memory per isolate holds at most 10,000 ids. The reference page no longer says a revocation stops a token at once: KV takes up to about 60 seconds to reach other locations.
- The example Worker takes its issuer from `ISSUER` in configuration, blocks unverified clients and leaves dynamic registration off; its sign-in compares `return_to` to `oauth.callbackUrl` and issues the code for the flow's state. The workerd test connects a metadata document client instead of a registered one.

Fixes from the re-review of the `oauth` kit:

- The token endpoint reads the body with the parser the library uses (`request.formData()`, values by `getAll`), and refuses a body with a `%` that starts no escape. Before, the kit parsed the raw text itself: under workerd a rotated refresh token sent as `refresh_token=<R1>%`, or with `grant_type=refresh_token%`, skipped the reuse check while the library refreshed with R1, so the attacker's copy lived on and the real client was locked out. `esbuild` and `miniflare` are now pinned devDependencies, so `oauth.workerd.test.ts` runs in `bun test` after `npm ci`. Without them it skips; the release check sets `OMAZY_REQUIRE_WORKERD=1`, so there it must run.
- A platform door needs a client policy with a non-empty `known` list, and blocks every other client by default (`others` and `unverified` both `block`). Setting either to `allow` there, or leaving `known` empty, throws at start unless the policy sets `dangerouslyAllowUnlistedClients: true`. Before, a platform door with no policy took any verified metadata document, so a look-alike "Claude" on any domain got to consent and a super admin token.
- `platformDoors` is required: name the doors whose seats have no tenant, or pass `[]`. The kit no longer guesses from a door called `platform`, so an operator door called `admin` got none of the platform rules. A seat with `tenant: null` is refused at any other door: at sign-in (`sign_in_failed` with `tenantless_seat`), in `keys.createPersonal`, and in `resolveSeat`. `keys.service.maxTier` above R3 throws at start unless `keys.service.allowR4` is set (`SERVICE_TIER_CAP`).
- The refresh lock is taken only for a token the grant holds: its SHA-256 (the library's own hash) must equal the grant record's `refreshTokenId` or `previousRefreshTokenId`. Any other token gets the reuse check without the lock and goes to the library, so a made-up token writes nothing to D1 and opens no Durable Object, and someone who knows a grant's id cannot hold its lock. A refresh that finds the lock held gets 503 `temporarily_unavailable` with `Retry-After`, not `invalid_grant`, which tells a client to drop the grant. `rateLimit.token` counts every POST to the token endpoint per address (`token:<ip>`, event `token_limited`, 429); the kit warns at start without it.
- A refresh token is marked retired before the library sees it, and the mark is removed only when the library refuses with a 4xx. Before, it was marked after the library answered, and the 10 s lock could lapse while the library waited up to 10 s on the client's metadata document, so a replay of the same token in that window passed too. Now any second presentation, at any time after the first began, is a reuse and revokes the grant. This was chosen over a longer lock with a deadline: a deadline is a timing guess, and aborting the library cannot undo a KV write it has started.
- A sign-in code that reaches the callback is spent even when the flow fails (no matching cookie, an expired state, a door mismatch, an `error`): the kit calls `authenticate` and drops the result. Before, an attacker could push his own state through a victim's sign-in; her browser failed at the callback, but the code stayed good in her history and logs and finished his flow as her. The callback also takes the code by form POST (`state`, `code`, `error` as `application/x-www-form-urlencoded`). The sign-in page should return the code by form POST, or after one click, never by an automatic redirect; the example Worker now shows a Continue button that posts it.
- The kit's metadata document check sends the library's own headers (its `User-Agent`, `Accept`, `Cache-Control: no-store`) with redirects refused, and requires the document it reads to match the library's: the same name and redirect URIs as `lookupClient`, the name the consent page shows, and the request's redirect URI listed. A difference is refused (`client_metadata_refused` with `mismatch`). Before, the check sent no `User-Agent`, so a server that redirected only the library passed it, and the library used the document it was redirected to. The library itself is not patched: it is a peer dependency the product installs, so a patch here would never reach a product's deploy. The gap left: two fetches, so a server can still redirect the library to a document identical to its own, which grants nothing.
- A request without the caller's address is refused (400, `request_refused` with `no_address`) wherever an address is counted: GET `/authorize` with `rateLimit.authorize` or Turnstile, the consent POST with Turnstile, the token endpoint with `rateLimit.token`, and registration. Before, every such request shared one bucket, `authorize:unknown`, so one caller behind a proxy or a service binding used up the limit for all. `clientIpHeader` names another header for a product whose own front sets it; the default is `cf-connecting-ip`.

Fixes from the final review of the `oauth` kit:

- A revoked grant stays revoked across locations. The library writes the whole grant back to KV on every refresh, and each location reads KV through a cache for up to about 60 seconds, so a refresh in a location that still had the grant cached wrote a revoked grant back: a thief caught by reuse detection, or an app the person had disconnected, kept refreshing. Every revocation (reuse, `revokeApp`, `personLostRole`, and the grant replaced when the same client connects to the same seat again) now writes a tombstone to the refresh store first, for the refresh lifetime plus an hour. The token endpoint checks it before the library sees a refresh token or an authorization code naming a grant in KV, `resolveSeat` after an access token validates, and `connectedApps` for each grant; a tombstoned grant is revoked again and answers `invalid_grant`. The reused token's mark is no longer dropped on reuse; it lives out its TTL. `RefreshStore` has two new methods, `tombstone` and `tombstoned`, which a custom store must implement. D1 needs the new table: run `applyOAuthD1Migrations` again (migration `0002_oauth_grant_tombstone`, additive), and `prune` clears expired tombstones. The Durable Object keeps the tombstone in the same object, with no new migration. On the KV default the tombstone has the same cache delay as the grant, so it cannot close this; a platform door already refuses that store without `acceptKvRace`.
- Per-address limits count an IPv6 address by its /64 (key `authorize:2001:db8:1:2::/64`), and an IPv4-mapped IPv6 address as its IPv4 address. Before, each address counted alone, so one host on one /64 sent 50 authorizations and 50 token requests through limits of 2, and never saw Turnstile. The value of `clientIpHeader` must be exactly one IPv4 or IPv6 address; anything else is no address and is refused where addresses are counted. A header any caller can send (`x-forwarded-for`, `x-real-ip`, `forwarded`, `true-client-ip` and similar) throws at start unless the new option `trustClientIpHeader: true` says the product's own front overwrites it. Events that carried the address now carry its bucket. MCP clients hosted on Workers reach the server from Cloudflare's own addresses, which many of them share; the docs say to size the limits for that.
- The door's client policy holds after consent. Every refresh, code exchange and `resolveSeat` checks the grant's client against the policy as it stands now, so a client the product blocks, or takes off a `known` list, stops at once: its refresh token and code answer `invalid_grant` (event `client_blocked`) and its access token resolves to no seat. Before, the policy was checked only at consent, so a blocked client kept refreshing for the life of its grant. The grant is kept, so allowing the client again brings it back. The check makes no network call: the status recorded at consent stands unless the lists move it, and only a client that was known and is no longer listed is looked up again.
- The docs say when the form POST callback works: the flow cookie is `SameSite=Lax`, so a POST carries it only when the sign-in page is on the same site as the issuer (`app.acme.com` to `mcp.acme.com`). A sign-in on another site uses the one-click GET: a Continue link to the callback with `state` and `code` in the query.

Fixes from the review of the N1 to N3 fixes in the `oauth` kit:

- A client's own revocation at the token endpoint (RFC 7009: `token`, no `grant_type`) tombstones the grant. The library revokes the whole grant for a current or previous refresh token the client holds, but the kit wrote no tombstone, so a refresh in a location whose KV cache still held the grant wrote it back and the revoked grant lived again everywhere. The kit now reads the grant first and tombstones it when the library answers 200 for a refresh token of that grant sent by its own client. Revoking an access token revokes only that token in the library, so it writes no tombstone. Fails closed: a tombstone that cannot be written answers `503` `temporarily_unavailable` (event `oauth_error`, code `revocation_unrecorded`). Nothing is revoked then, so the retry works; for a confidential client see the fix below.
- A client taken off a door's `known` list stays known by its host only when its redirect URIs are bound to that host. The grant now records which list made the client known at consent (`knownBy`: `id` or `domain`). Before, a client known by its exact id, delisted while its host stayed in `knownDomains`, kept `known` without its redirect URIs being checked, though a fresh consent for the same client was refused. Now a client known by id and off the list is looked up again, and so is a grant from before this change; a client known by its host stays known while the host is listed.
- A delisted client is looked up once in five minutes per server instance, not on every call. Before, every refresh and every `resolveSeat` of a metadata document client that had come off the `known` list fetched its document again. The lookup now also takes the consent's redirect check: a document that redirects is refused (`client_metadata_refused` with `redirect`) and its grant stops.
- `refresh.tombstoneCacheSeconds` (0 to 5, default 0): `resolveSeat` may remember per server instance that a grant has no tombstone, and skip the refresh store for that long. With a consistent store every MCP request that carries an access token makes one store call; this trades that call for a delay of up to that many seconds before a revocation made in another isolate stops an access token. A revocation by the same instance applies at once; refreshes, code exchanges and `connectedApps` always read the store. `connectedApps` now reads every grant's tombstone and last use, and the keys, at once instead of one after another. The docs recommend the Durable Object store for heavy MCP traffic.
- An IPv6 /48 counts as one caller too. A /64 bucket still left 65,536 of them to anyone with a /48, which a free tunnel broker hands out: 200 token requests from one /48 at a limit of 2 were never limited. Two new optional bindings, `rateLimit.authorizePer48` and `rateLimit.tokenPer48`, count every IPv6 request by its /48 as well (`token:2001:db8:1::/48`), after its /64; bind them with a higher limit than `authorize` and `token`. Without them the kit warns at start. Registration counts the /48 at `registration.perHourPer48`, default ten times `perHourPerIp`. A 6to4 address (2002::/16) counts as the IPv4 address it carries. Limit events name the bucket that ran out.
- An authorization code presented twice tombstones its grant. The library revokes the grant when a used code comes back (RFC 9700), but wrote no tombstone, so a refresh in a location whose KV cache still held the grant wrote it back. And a location whose cache held the grant from before the exchange exchanged the same code a second time. The kit now records each code exchange in the refresh store, under the grant's lock, for the code's ten minutes (dropped when the library refuses the code), and answers a code that comes back from the grant's own client, once authenticated: tombstone, revocation, then `400` `invalid_grant` "Authorization code already used", with the new event `code_reuse`. Another client or a wrong secret gets the library's own answer. A tombstone that cannot be written answers `503` with nothing revoked. On the Durable Object store each exchanged code leaves a mark in the grant's object for ten minutes.
- A confidential client's own revocation (RFC 7009) now fails closed like a public client's. Before, the tombstone followed the library's 200, so a failed write left the grant deleted in one location and not tombstoned. The kit now has the library authenticate the client alone (the same credentials on a revocation of a token that names nothing), then tombstones and revokes the grant itself; a failed write answers `503` with nothing revoked, and the retry finishes the job. It works for every client authentication method, `private_key_jwt` included.

Fixes from the fifth review of the `oauth` kit:

- The kit reads which client a token request names with one function, `tokenRequestClient`, copied from the library's own client authentication (`parseBasicAuthorizationHeader` and `parseTokenEndpointRequest` in 1.3.0), and the body with the same `tokenForm` as before, both now in `src/oauth/token-request.ts`. The scheme of the Authorization header is the text up to the first space or tab, compared without case; any scheme but Basic is ignored and the client is read from `client_id`, then from a client assertion's issuer, as the library reads it. Before, the kit read any Authorization header that was not Basic as naming no client while the library ignored it, the third time a difference in reading a request let one through. A new test, `oauth-parity.test.ts`, runs a table of awkward requests (Bearer, Basic in mixed case, extra spaces and tabs, bad base64, a bad escape, duplicate `client_id`, client assertions) through the kit and the library under Bun and under workerd, and fails when they name different clients.
- A used authorization code is never handed to the library again. With an Authorization header that was not Basic, the grant's own client replaying a code at a location whose KV cache still held the grant from before the exchange went to the library there, which exchanged it a second time and minted a second token set. The replay is now caught for the grant's own client (tombstone, revocation, `code_reuse`), and once the kit's record shows the code was used any other request, from another client or naming none, gets `400` `invalid_grant` from the kit with nothing revoked.
- Someone holding a code without its verifier can no longer make the real client's first exchange count as a replay. Naming a client whose metadata document he served slowly, he held the grant's lock while the kit recorded the code as used; the 10 second lock lapsed while the library waited, and the victim's exchange was then answered as a replay, which revoked her grant. Now only a request from the grant's own client is locked and recorded; any other goes straight to the library, which refuses a code issued to another client first. The record is pending, with its lock's holder, until the library answers, then dropped on a 4xx or kept as used. A request that finds an exchange still pending gets `503` `temporarily_unavailable` (event `refresh_contended`), not a replay's answer. The lock for a refresh or a code exchange is now 30 seconds, above the library's worst case (10 seconds on a metadata document, 10 on its keys).
- A client's own revocation (RFC 7009) tombstones the grant whatever its Authorization header. A confidential client that sends its access token as `Bearer` on every call, and its credentials in the body, had its revocation read as naming no client, so the kit handed it to the library with no tombstone and a location whose KV cache still held the grant wrote it back on the next refresh. The revocation now reads its client with `tokenRequestClient`, like the code exchange.

The `ai` kit, experimental: the run layer every model call passes through.

- A new entry point, `@omazyai/sdk/ai`. Every model call belongs to a unit: `task()`, `actorUnit()`, `copilotUnit()` or `workflowUnit()`. A manifest names the owner, the surfaces, a model role (never a model name) with a fallback role, temperature and output limit, a versioned prompt per language, a context recipe, memory scopes, the tools and their highest tier, the output schema or target capability, the evals file and the caps per run and per day. A manifest that breaks a rule throws `UnitError` when the module loads.
- `createAi({ omazy, runs, prompts, guard, registry, memory, layers, retrievers, ... })`. `ai.run(ctx, task, input)` builds the context, checks the caps, makes one structured call, checks the output and saves it through the target. It never throws for a refusal. `ai.start(ctx, unit)` opens a run for a unit that holds a conversation, with `context`, `complete`, `stream`, `structured`, `call`, `propose` and `finish`.
- Every call carries `metadata` (unit, unit version, prompt version, run id; and `role` when the product's role map turned the role into a model name the platform cannot read it from, if a key is free), `model: "role:<name>"` (or the product's own role map), the unit's temperature and output limit, and `cache_ttl: 0` when the context holds live data.
- `ai.resume(ctx, unit, runId, { vars, tags })` opens an earlier run again in a later request, bound to the same row: usage carries on, the run cap keeps counting what it spent, and effects continue its sequence. It throws `ResumeRefusal` (`not_found`, `finished`, `other_seat`, `other_unit`, `other_version`) for a finished run, another tenant, seat or person, or another unit, unit version or prompt version.
- `role` on `scope.complete`, `scope.stream` and `scope.structured` uses another role for one call, only one the manifest declares (`model.use`, `model.fallback`, `attachments.vision`), tried alone with no fallback. The platform records the role from `role:<name>`; the run keeps the last one.
- Caps before the call: today's spend in the run store plus the run's estimate, per unit in the tenant and, as the product sets them, per tenant, person and product. A run's own cap is checked before each further call. A 402 from the platform is a cap refusal. Usage is summed on the run; cost comes from `usage.cost_micros`, else the product's rate card, marked estimated.
- Product tags: `tags` on a unit, a run and a call go out in the same `metadata`, checked against the platform's rules (at most 8 keys, `role` reserved; `[a-z][a-z0-9_.-]*` up to 40 characters, values up to 200 bytes) before anything is sent.
- Task output is forced through `response_format` with a JSON Schema, falling back to one forced tool call when the model cannot take a schema, and is checked before anything is saved.
- A run record per run and an effects ledger with one row per capability call through the guard. Calls outside the unit's tools or above its tier are refused before the guard and recorded; a write already made in the run is never sent again.
- The context builder: platform, tenant, role, surface, unit, memory, retrieved, conversation and untrusted, in that order, with a token budget per layer and for the call, the fixed layers first so the prompt cache hits, memory and retrieved text fenced as data, outside input fenced as untrusted and kept out of templates, and compaction recorded. Tokens are estimated without a tokenizer.
- Memory: working memory and known ids on the run, conversation threads held to one person in one tenant, and long-term memory per person or per tenant that a model proposes and a person confirms. Scope is in every store query; unconfirmed memory never reaches a prompt; `list`, `forget` and erasure by person, mention or tenant.
- `MemoryStore.listThreads(owner, { limit, cursor })`: a person's threads in one tenant, newest change first, 20 a page (at most 100), with an opaque cursor. In memory and in D1, on the `ai_threads_owner` index.
- Threads are keyed by tenant, person and id, in memory and in D1. Before, a thread was keyed by its id alone: when a second person used an id someone else had, their turn failed with "thread belongs to another person" and the thread never reached their `listThreads`. Now each has their own. `ai_threads` has the key `(tenant, person, id)`, `ai_turns` carries tenant and person with the key `(tenant, person, thread_id, seq)`, and `ai_threads_owner` covers `(tenant, person, updated_at)`. A person with no tenant is stored with tenant `''`; an empty tenant id is refused with `RangeError`. This changed the unreleased `0001_ai` migration in place: drop and recreate any local or test database made before it, since `CREATE TABLE IF NOT EXISTS` leaves the old tables as they were.
- Prompt templates from the product's own map, by key, version and language. Every run records the version and language.
- `checkUnits()` and `findDirectModelCalls()` for a product's CI.
- Stores for Cloudflare D1 (`d1RunStore`, `d1MemoryStore`, with the SQL in `AI_MIGRATIONS`) and in memory.
- A second entry point, `@omazyai/sdk/ai-sdk`: `omazyModel(run)` is a Vercel AI SDK `LanguageModelV4` for `generateText`, `streamText` and the tool loop, running every call through the run. `@ai-sdk/provider` 4.0.39 is an optional peer dependency, used for its types only.
- `aiSdkTools(run, registry, { names, onOutcome })` builds AI SDK tools from the registry, each one's `execute` going through `run.call()`, so the unit's tools and tier, the guard and the effects ledger apply. The model reads the result or what happened instead, never a confirm token; `onOutcome` hands the full outcome to the product's UI. Tools built by hand bypass the guard.

The `actors` kit, experimental: a form as a conversation. Code owns the order of questions, every check, the card and the submit; the model only reads.

- A new entry point, `@omazyai/sdk/actors`. `actor({ id, target, slots, model, prompt, attachments, ... })` names the one capability it submits. Its slots come from the target's input schema, in the order the actor lists them, with dependencies (`after`), conditions (`when`), defaults, derived slots (`derive`, never extracted or asked), lookups, checks, a confidence threshold per slot, and the product's own validators. A bad actor throws `ActorError` when the module loads; a slot the target lacks, or a lookup above R1, throws when the runtime is built. The target must be R2 or higher, so a person's confirm or an approval through the guard always stands before the change: an R0 or R1 target throws `ActorError` at definition when `target` is the capability itself, or when the runtime is built from its name, and a target whose `riskFor` drops an input below R2 gets no card (`tier_below_confirm`).
- One structured model call per turn through the ai kit's `scope.structured`, forced through a closed schema of `{slot, value, confidence, evidence, from}` items, corrections included. A turn with an image asks for the actor's `attachments.vision` role for that call only, in the same unit and run. The person's message, attachments and the values so far are fenced as untrusted; the prompt (`EXTRACT_PROMPT`) holds only code's text.
- Code applies the items: unknown, derived and non-extractable slots are dropped and recorded on the turn; values are read by the slot's `parse` or its schema type (commas, Bangla digits, yes and no, enums); a value below the threshold is asked about ("I read BDT 25,000.00 for the amount. Is that right?"), never filled; the message and an attachment that disagree become a choice; a correction moves the slot, re-resolves what depends on it, and is said.
- Ids are never taken from the model: a lookup slot keeps what the person wrote as a query and resolves it through a guard-checked read. One match fills it, two or more become a choice, none is said. Checks such as "this bank reference is not used" are guard-checked reads too; schema checks and the target's own parse run before the card.
- The clarifier asks for the next slot that is missing or in doubt, from templates in English and Bangla (Bangla numerals, lakh grouping), with choices when they exist. A product changes a sentence or adds a language through `text`, and may reword a question through `phrase`; choices never change.
- The confirmer's card lists every value with its source (message, attachment, lookup, person, default, derived, prefill) and its evidence. At R2 it carries the guard's preview and holds the confirm token. Only `runtime.confirm(ctx, session, cardId)` calls the target, for the person who owns the session and the current card: R2 runs, R3 and R4 become `pending_approval`, and `status()` settles it once the approval is decided.
- `handoff()` at any point returns the form's pre-fill (filled, default and derived values, never a doubtful one), the values still in doubt, and the product's link. Sessions expire after 24 hours idle; `expireIdle(store, now, { runs })` expires the ones nobody came back to, from a cron. Every turn is recorded on the session. A session is one run of the actor's unit, opened again each turn with `ai.resume`: every model call, lookup, check and the submit, ending with the session.
- Session stores with compare-and-swap on the session version: `memorySessionStore`, `d1SessionStore` and `pgSessionStore` (the same SQL in `ACTOR_MIGRATIONS`, Postgres through any driver's `query`), and `ActorSessionObject` with `durableObjectSessions(namespace)` for one Durable Object per session. `drafts` mirrors every write to a second store, so a session in a Durable Object resumes from another surface through D1. `resume()` finds a person's newest open session.
- Surfaces: `actorTools(runtime, { audiences, permission })` gives `actor_start`, `actor_reply` and `actor_status` as R1 capabilities for an MCP door. They never submit. At the card they name the target call, which the client makes on the same door, so the guard asks the person (R2) or holds it for approval (R3). `copilotActorStep(runtime)` gives a copilot one `actor_start` tool and routes the person's later messages to the open session by code.

The `testing` kit, experimental: what a product needs to test its units, actors and doors without the network, and to gate a release on them.

- A new entry point, `@omazyai/sdk/testing`. `fakeCore()` is an in-process Core API: a `fetch` and a real `Omazy` client on it. Replies are scripted in order, by a rule on the request (`fake.on('unit_id', ...)`), or by a function: text, structured output (the `output` of a `response_format` call, or the input of the forced tool), tool calls, usage, `cost_micros` from a rate card, streamed `delta` and `done` events, and refusals (`reply.cap()` for 402 `BUDGET_EXCEEDED`, `reply.unsupported()`, `reply.down()`). `budgetUsd` and `maxCalls` refuse with 402 once spent; `structured: 'unsupported'` tests the forced-tool fallback. Every request is recorded with its tags and role. `memoryAdapters()` gives fresh in-memory stores for every kit.

A `RunResult` from `ai.run` is read for its output and usage. The report is JSON; `formatReport` gives a few lines for CI and `assertEval` throws `EvalFailure`. A set under 30 cases gets a warning.

A fixture naming a tool the registry lacks throws.
- `judge({ rubric, omazy })`: rubric grading by a model on the published role `extract.strong` (`JUDGE_ROLE`), so it runs on any account; `role` names another, as runs of the kit's own `eval_judge` task through the AI kit, so every call is tagged and capped, never cached, and the graded reply is fenced as untrusted. `BANGLA_REGISTER` is RFC-0901's Bangla register rubric.
- `autoevals` 0.5.0 is an optional peer dependency. `fromAutoevals(scorer)` wraps any of its scorers; `autoevalsClient({ omazy })` is an OpenAI-shaped client for its model-graded ones, whose every call is a tagged, capped run of `eval_autoevals`, on `extract.strong` by default.
- The injection suite: `INJECTION_FIXTURES` (hostile visitor text, attachment text, website text and staff names, in English and Bangla), `obeyingModel()` for a model that does what the text asks, `spyGuard()` to record what reaches the guard, and `injectionSuite`, `unsafeEffects` and `assertNoUnsafeEffects`: no R3 or R4 ran, no approval was decided, no R2 ran without the token of a card shown for the same arguments or was confirmed upstream, and the text never reached a system prompt outside a fence.
- `assertRouteContract()` holds the pinned SDK's route table against the platform's published route contract, for a product's CI. `uses` limits it to the routes the product calls.

- The testing page has a guide to promptfoo red-team runs against an MCP door, as a CI tool and not a dependency, checked against promptfoo's documentation: the door is attached to a model target with `config.mcp`, the token read with `{{ env.NAME }}`, `jailbreak-templates` in place of the deprecated `prompt-injection` and `redteam.language` in place of the deprecated `multilingual`, and each claim linked to its page.
- A unit manifest may carry its pass mark: `evals` takes `{ path, threshold }` as well as a plain path, checked when the module loads (a `.jsonl` path, a threshold from 0 to 1). `evalsOf(unit)` reads either form. `evalUnit` takes the threshold from its option, then the manifest, then the set's `$meta`, then 0.9.

The `flows` kit, experimental: workflows and automations whose steps are capabilities through the guard, ai tasks or actors, each step in a ledger.

- A new entry point, `@omazyai/sdk/flows`. `workflow({ id, version, steps })` with `step.read`, `step.write`, `step.task`, `step.actor`, `step.notify` and `step.bulk`. Each step has `when`, `args` from the state (`s.input` and every earlier step's output by id), and `stop` to end the run with a reason. `skipIf: 'not_built'` records a step whose capability does not exist yet as `skipped` and hands `todo` to a person. A bad definition throws `WorkflowError` when the module loads.
- Every capability call goes through the ai kit's `callInRun`, so the guard decides it and the effects ledger records it, under a run of the workflow (its id and version as the unit, its capabilities as tools, R3 at most by default). The effect's request id is `<run key>:<step>`. That ledger is the run's one record: guard calls are tagged with their step, and what the run decides itself (`planned`, `skipped`, `waiting`, `failed`, `refused`) goes in through `ai.recordInRun`. `flows.steps(key)` folds the rows into where each step stands; `createFlows` takes `runs: ai.runs` for it.
- Writes never retry (`retries: { limit: 0 }`). A failed or refused write goes to a person through `handoff`, and the run waits until they settle it with `flows.resolve(key, step, { action: 'continue' | 'stop', output? })`, or ends `failed` after `resolveTimeout` (7 days by default). Reads keep the runner's retries; a read refused by the guard ends the run `stopped`. An R2 write runs only when the step says the person confirmed it upstream (`confirm: 'upstream'`); otherwise it goes to a person.
- R3 writes create their approval and the run waits for it with `waitForEvent`. `flows.onApproval` is the guard's `onApproval` hook and wakes the run on every event after the request, `failed` and `stale` included; `flows.approvalSettled(id)` is a fallback for a guard whose events cannot reach it. An approved change becomes `done` with its result, a refusal `refused` and the run goes on, an expiry or a stale state goes to a person.
- Bulk steps run one capability over many items in chunks (25 by default, at most 100), one durable step per chunk, and refuse before any item when the chunks would pass the run's step cap (1,000 by default). A chunk with failed writes goes to a person.
- Dry run: reads run, every write goes to `guard.preview` through `ai.previewInRun`, so permission, tenant and tier apply, and records `planned` or the refusal; actors and notices are not started or sent, and `report` gets the lines ("level: would set tA from essential to professional", "add: would go to a person to confirm: add x").
- `nothingToReport(s)`: notices are recorded `skipped` and not delivered, and the run says `reported: false`.
- Runs are idempotent by key, such as `fulfil:<payment id>`: `createFlows(...).start` and automations claim the key in the store before the runner, and a second start answers `exists`.
- Automations: `automation({ id, on, run, instanceId, owner, budget, mode })` with `on.event(type, match)`, `on.schedule(cron, { tz })` and `on.condition(cron, check, { tz })`. `createAutomations(...)` gives `enable`, `disable`, `setMode`, `dispatch(event)` and `tick(at)` for the scheduled handler. An automation runs under the seat of the person who enabled it, who must hold the owner role; when they lose it the automation turns off and its running runs stop at the next step. Budgets per day and month, in runs and in model spend; a refused or empty run is recorded (`refused`, `nothing`) and never delivered. A switch key `automation:<id>` stops it, as does `disable`. It starts in dry run.
- Runners: `flowEntrypoint(WorkflowEntrypoint, workflow, deps)` for Cloudflare Workflows (the product passes Cloudflare's base class, so the kit never imports `cloudflare:workers`), `cloudflareStarter(bindings)` to start runs and send events, and `memoryRunner` for tests, which replays runs from step results as Workflows does. A Node runner comes later.
- Stores: `memoryFlowStore` and `d1FlowStore` with the SQL in `FLOW_MIGRATIONS`: runs, links and automations. There is no step table.
- The worked example is Joya's payment fulfilment (RFC-0901 W29) in dry run, `sdk/typescript/examples/flows-payment-fulfil.ts`, and on Workflows in `examples/flows-worker.ts`.

Follow-ups across the `guard`, `ai` and `flows` kits, from the flows kit's open questions:

- `onApproval` gets `failed` and `stale` from `guard.execute` (and from `decide`, which runs it) when an approved change fails, a check at execution refuses it, or its target moved. Each is sent once, when the approval row changes.
- `guard.preview(ctx, name, args, opts?)`: the checks of `guard.call` (switches, arguments, tenant, `can()`, tier ceiling, `readOnly`) and the capability's preview, without running it, minting a token or asking for an approval. It answers `next: 'run' | 'confirm' | 'approval'`, is not rate limited, and is logged with the method `tools/preview`.
- The ai kit's effects ledger takes a workflow's step records. New outcomes `planned`, `skipped`, `waiting`, `failed` and `refused` (and `not_found`, which the guard already gave), and new columns `step`, `step_kind`, `message`, `ref` and `preview`, added to the unreleased `0001_ai` migration in place. `ai.previewInRun` records a dry run's preview-only effect through `guard.preview`; `ai.recordInRun` records a step state that is not a guard call; `callInRun` takes `{ step }` to tag its row. A guard row now carries the refusal's sentence or the preview's summary.

Dry run previews writes through `guard.preview`, so permission applies, and reports a refused write and an R2 write that would go to a person to confirm. The flows page states the R2 rule: a write runs only with `confirm: 'upstream'` on its step.
- Schedules take an IANA time zone through `Intl`, with no dependency: `on.schedule(expr, { tz: 'Asia/Dhaka' })`, or `{ tz: 'tenant' }` with `timeZone(tenant)` on `createAutomations`, so "Sunday 09:00 tenant time" works per tenant. `cron(expr, { tz })`, `matches(at, tz?)`, `localTime`, `localMinute` and `isTimeZone`. Fields are wall-clock time across a daylight saving change; a schedule's run key is the local minute, so a repeated hour starts one run. ## 0.4.0 (2026-11-23)

The Enterprise API: one workspace per customer. Nothing in 0.3.0 changed its name or its shape.

- A second client for a product that serves many customers, each in a workspace of their own: `OmazyEnterprise` in TypeScript and Python, `omazy.NewEnterprise` in Go. It takes an account key (`eak_...`), not an install token.
- Create the workspace of a customer, with its agent, its plan and its install, and get that customer's Core API token once. Your own id for the customer (`external_id`) makes the call safe to repeat: a repeat returns the same workspace and no token, so the client retries it like a read.
- List the account's workspaces page by page or all at once, find one by your own id, read one, rename and rebrand it, suspend and resume it, close it and reopen it.
- Rotate a customer's install token, with the old one kept for an overlap. This is never sent twice by the client.
- `core(token)` (`Core` in Go) gives the Core API client for one customer on the same deployment, so a product picks a customer's token and calls models, knowledge and the agent as that customer.
- An account key never reaches the Core API, and an install token never reaches the Enterprise API.
- The routes are listed in a contract of their own, `contracts/enterprise-api.routes.json`, and each client's tests are held to it.
- An account key is issued by Omazy to a product. There is no self-serve way to get one yet.

The agent's settings, under a new scope `agent:configure`:

- Read how the agent runs and change it from your backend: the model it answers on, the cap on one reply, the temperature, and the loop switches (the shared agent loop, streaming, masking of personal data, `memory`, which gives the agent remember and forget tools, and `files`, which gives it a create_file tool). `agent.settings.get` and `agent.settings.update` in TypeScript and Python, `Agent.Settings` and `Agent.UpdateSettings` in Go.
- A change names only what changes. Null puts a setting back to what the agent inherits: `null` in TypeScript, `None` in Python (an argument left out is `UNSET`), `omazy.Clear` in Go beside `omazy.Set`.
- A new model is tested with one real call before it is saved. `403 MODEL_NOT_AVAILABLE` is a model the plan does not allow; `422 MODEL_NOT_SERVING` is one that did not answer. Nothing changes in either case.
- The same change sent twice leaves the same settings, so the client sends it again after a 429, a gateway error or a dropped connection.
- A token made before this release does not hold `agent:configure`. Scopes are fixed when a token is made, so make a new one.

Live speech to text, on the existing scope `voice:speech`:

- `voice.transcribeStream` in TypeScript, `voice.transcribe_stream` in Python, `Voice.TranscribeStream` in Go: a WebSocket session that hears audio while the person speaks, so the text is ready a few hundred milliseconds after they stop instead of after the whole recording is uploaded and heard.
- Send audio as it is captured (`pcm_s16le`, `mulaw`, `alaw` with a sample rate, or `auto` for WebM/Opus, Ogg or WAV). `commit` after each utterance returns its final; `end` returns every final joined and the audio length it is billed by; `keepalive` holds a quiet session. Frames are `ready`, `partial`, `final` and `done`; an `error` frame arrives as the client's error with its code and request id.
- Voice minutes are counted once per session with a one-minute floor. Hold one session for a conversation and commit per utterance.
- The token goes on the upgrade: run it on your server, and relay from a browser. Zero dependencies: TypeScript uses the runtime's WebSocket (Cloudflare Workers, Node 22 and later, Bun, Deno; `webSocket` to bring another), Python and Go carry a small client of their own.
- `terms` on `voice.transcribe` (trailing arguments in Go): names and words to expect, so "Rashed Karim" is not heard as "Rasht Kareem". At most 200; more is refused, never cut.
- The contract marks a WebSocket route with `websocket`, and each client's tests hold its list to it.

Control over the gateway's response cache on completions:

- `cache_ttl` on `ai.complete` and `ai.stream` (`CacheTTL` in Go): leave it out for the gateway's own setting, `0` for a reply that never comes from the cache, or 60 to 2592000 seconds to bound how long a stored reply may be served again. Send `0` on any request that carries live data.
- `cache_hit` on the result (`CacheHit` in Go) says the reply came from the cache. Such a reply cost nothing and used no AI turn.

Agent turns that stream and take the person's context, on the existing scope `agent:run`:

- `agent.stream` in TypeScript and Python, `Agent.Stream` in Go: the reply arrives in pieces as the agent writes it, then the whole turn. The frames are a streamed completion's. In TypeScript `StreamEvent` takes the result type, `StreamEvent<AgentTurnResult>`; `StreamEvent` alone is still a completion's.

- `context` on a turn (`Context` in Go): one object of at most 2048 bytes about where the person is, read by the agent as a hint, as a widget page's context is. `{"interaction": "voice"}` makes it answer for the ear.

The agent's MCP servers, under a new scope `agent:tools`:

- Connect, list, read, change and remove the MCP tool servers the agent may call: `agent.mcpServers` in TypeScript, `agent.mcp_servers` in Python, `Agent.ListMCPServers` and its siblings in Go. For a product with a workspace per customer, this is how each customer's agent gets that customer's tools.

- The endpoint must be https on a public host, or the call is refused with `400`.
- The credential is write-only. No call returns it.

## 0.3.0 (2026-11-20)

Idempotency keys. Nothing in 0.2.0 changed its name or its shape.

- A request that changes something takes an idempotency key: placing a call, posting a message, publishing, running an agent turn, starting a voice job, adding a document, importing a file, adding a source and crawling one. With a key the platform runs the request once and answers a repeat with the first answer, and the client retries the request the way it retries a read. Without a key these are still sent once.
  - TypeScript: a last argument `{ idempotencyKey }`. `agent.turn` takes an `AbortSignal` as before, or `{ signal, idempotencyKey }`.
  - Python: a keyword argument `idempotency_key`.
  - Go: `omazy.WithIdempotencyKey(ctx, key)`.
- A repeat that arrives while the first request is still running (`409 IDEMPOTENCY_IN_PROGRESS`) is waited out and sent again. The same key with a different request (`422 IDEMPOTENCY_KEY_REUSED`) is an error.
- The last response says whether it was a replay: `last.replayed` in TypeScript and Python, `Last().Replayed` in Go.
- `whoami` reports the plan's voice minutes next to its AI turns. Speech, voice jobs and call placement answer `402 PLAN_LIMIT_REACHED` when the minutes are used up.
- The error of a failed stream carries the API's own error code.
- Fixed: a voice job named its app in the request body, where the API did not read it, so a workspace with more than one app always got its default app. The app now goes in the query string.

## 0.2.0 (2026-11-20)

Knowledge documents. Nothing in 0.1.0 changed its name or its shape.

- Read and write the agent's knowledge base: list, read, add, change and delete a document, with how its indexing stands (`queued`, `indexing`, `ready`, `failed`). Reads need `kb:read`, writes `kb:write`.
- Upload a file (PDF, spreadsheet, image or text) as a document.
- List the websites a knowledge base is crawled from, add one, and crawl it again.
- Export what changed in the knowledge base since a version, with the passages search uses, to keep a copy of your own.
- The body of the `kb.updated` event is typed in the TypeScript client (`KnowledgeUpdatedEvent`). Verify it with the signature helper every client already has.
- Knowledge writes are never sent again by a client after a failure. The reads are, as other reads are.
- Fixed: the TypeScript and Go types named a voice job kind `notes`. The API takes `transcribe` and `meeting_notes`.

## 0.1.0 (2026-11-19)

First release.

- Every Core API route over HTTP: completions (whole or streamed), knowledge search, agent turns, speech, outbound calls, voice jobs, customers, conversation messages, page publishing and session credentials.
- The Core API's MCP server: list tools, call a tool, or get the URL and headers for another MCP client.
- One error type with the status, the stable code, the message and the request id.
- Retries on 429, 502, 503, 504 and dropped connections, only for routes that are safe to send twice.
- The request id, the rate limit and the token's deadline readable after each call.
- `whoami` reports the workspace's plan: its rate per minute and the AI turns used and included.
- Signature verification for requests the platform sends to your server.
- TypeScript only: `@omazyai/sdk/server` with the flow and context request shapes, block builders and an MCP tool server for a Worker.
